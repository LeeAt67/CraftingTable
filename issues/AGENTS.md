# 问题跟踪规范（issues/）

本目录是 CraftingTable 的**缺陷事实源**。任何 agent 或开发者在修复 bug 之前，必须先在这里确认是否已有对应 issue；修复之后，必须回写状态、提交与回归测试。

> 这是仓库级约定：根目录 [AGENTS.md](../AGENTS.md) 的「问题跟踪」一节指向这里，两处必须同时维护。新增、关闭或改动 issue 时，先读本文件。

## 1. 目录结构

```text
issues/
  AGENTS.md              ← 本文件：维护规范
  README.md              ← 索引：模块 → issue 列表与状态
  <module>/              ← 按模块分目录，一个模块一个目录
    BUG-001-<slug>.md
    BUG-002-<slug>.md
```

模块目录按代码归属划分，不按发现人、日期或严重级别划分。当前已登记：

| 模块目录 | 覆盖范围 |
| --- | --- |
| `docs/` | 文档工作区：`/docs` 路由、目录树、编辑器、自动保存、搜索、导入导出 |

其它模块（`today/`、`agent/`、`platform/`）在该模块出现第一个 issue 时才建目录，不要预建空目录。

## 2. 命名规则

```text
BUG-<三位序号>-<kebab-slug>.md
```

- 序号在**模块内**独立递增，从 `001` 开始，一经使用永不复用，即使 issue 已关闭。
- slug 用英文小写与连字符，描述现象而非结论。例：`opennode-race`、`save-status-cross-document`。
- 重命名文件等于丢失历史引用；只有写错 slug 时才允许改名，并在索引里保留旧名备注。

## 3. 必写章节

每篇 issue 必须包含以下章节，缺任何一节都视为文档未完成：

1. **元信息表**：状态、严重级别、模块、发现日期、发现方式、影响版本、当前分支。
2. **S — 背景（Situation）**：涉及的代码路径、组件、数据结构，让没读过这块代码的人能看懂上下文。
3. **T — 期望（Task）**：按设计规范应该发生什么，附设计文档章节链接。
4. **A — 复现（Action）**：可执行的步骤，包含前置状态、操作序列、注入条件（延迟、断网、超长输入等）。
5. **R — 实际（Result）**：实测观察到的结果，附证据（控制台输出、断言报错原文、截图路径）。
6. **根因**：定位到具体文件与行，说明为什么会这样。
7. **修复建议**：最小改动方向，注明涉及的文件。
8. **验证方式**：怎么证明已修好，必须给出可执行的命令或回归用例名。
9. **关联**：相关设计规范、实施计划、提交哈希、其他 issue。

## 4. 登记门槛（重要）

只有**能被验证**的问题才能登记为 bug：

- 页面可复现：在真实运行的应用里按 A 步骤操作，能稳定看到 R。
- 或确定性测试可复现：给出能稳定失败的最小用例，并说明失败断言。

仅靠阅读局部代码推测出的「可能的 bug」**不得**登记为 issue。这类观察写进对应 issue 的「风险观察」小节，或写进设计规范的已知限制，并明确标注「未复现」。

判定顺序：先跑页面，再用确定性测试兜底。两者都做不到，就不是 issue。

## 5. 状态流转

| 状态 | 含义 |
| --- | --- |
| `待修复` | 已确认，尚未动手 |
| `修复中` | 有进行中的分支或提交 |
| `已修复待验证` | 代码已改，回归用例待跑或待人工确认 |
| `已关闭` | 回归验证通过，附验证证据 |
| `不复现` | 尝试复现失败，保留记录与尝试过程，不删除 |

状态只前进不跳跃；`已关闭` 必须附验证命令与结果。关闭后再次出现时，把状态改回 `待修复` 并追加「复发记录」小节，不新建同序号文件。

## 6. 索引同步

[README.md](./README.md) 是入口列表。每次新增或改变状态，必须同步更新：

- 新增 issue → 在对应模块表格追加一行：编号、标题、严重级别、状态、发现日期。
- 状态变更 → 改该行状态列。
- 不得只在 issue 文档里改状态而漏掉索引；索引与文档不一致时，以文档为准并立即修索引。

## 7. 严重级别

| 级别 | 判定 |
| --- | --- |
| `P0` | 数据丢失、崩溃、核心流程不可用 |
| `P1` | 功能错误：用户看到错误状态、错误内容或无法恢复 |
| `P2` | 体验问题：信息不清、需刷新绕过、次要流程受影响 |
| `P3` | 边界与一致性问题：排序、文案、非关键提示 |

## 8. 与其它文档的关系

- **需求**归 [docs/requirements.md](../docs/requirements.md) 管，issue 不重复登记需求。
- **设计**归 `docs/superpowers/specs/` 管。issue 可以指出实现与设计不符，但改设计要走设计流程，不能只在 issue 里改口径。
- **实施计划**归 `docs/superpowers/plans/` 管。issue 修复任务可以引用计划中的任务编号。
- issue 只描述「哪里坏了、怎么坏的、怎么确认修好了」。

## 9. 修复流程

1. 确认 issue 存在且状态为 `待修复`；不存在则先登记。
2. 状态改为 `修复中`，在 issue 里写下分支名。
3. 先写失败测试（或先跑通人工复现步骤），再改代码。
4. 状态改为 `已修复待验证`，补「修复提交」与「回归用例」。
5. 跑门禁（`pnpm typecheck`、`pnpm test`、`pnpm test:go`、相关 e2e），把结果写进 issue。
6. 状态改为 `已关闭`，同步索引。

## 10. 写作要求

- 全部使用中文；代码标识符、命令、报错原文保持原样。
- 复现步骤用有序列表，一步一个动作，不写「适当操作」「类似地」。
- 证据引用真实输出，不要改写或概括报错文本。
- 不写修复者的推测性结论；不确定就标注「待确认」并说明还需要什么证据。
